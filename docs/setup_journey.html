§ 01 / PREFLIGHT

Check AWS credits & domain before spending

Open-source software has zero license fees, but EC2 compute, EBS storage, and Elastic IPs still bill your AWS account.

Before provisioning

Start in the AWS Billing and Cost Management console. Verify your promotional credit balance, expiration date, and which EC2/EBS services are covered. At the same time, create an AWS Budget alert so an accidental oversized instance never surprises you.

Verify AWS credits

Open AWS Console → Billing and Cost Management → Credits. Confirm active credits and expiry date.

Create a monthly AWS Budget

Go to Budgets → Create budget → Zero spend / Cost budget. Set a monthly threshold (e.g., $15 and $30) with email alerts at 80% and 100%.

Prepare a domain name (recommended for HTTPS)

Caddy automatically provisions Let's Encrypt TLS certificates when DOMAIN_NAME points to your server's public Elastic IP. If you skip a domain for now, Caddy falls back to self-signed TLS on localhost, and n8n webhooks will only be reachable internally or via SSH/SSM port forwarding.

LOCAL TEST OPTION FIRST

Want to test the whole stack on your Windows/Linux laptop before creating an EC2 instance? Start Docker Desktop, copy .env.example to .env, run python supporting_codes/generate_secrets.py, and run docker compose up --build -d. Everything below applies identically to EC2.

§ 02 / COMPUTE & DISK

Provision the AWS EC2 server

Ollama is the memory-hungry component; size the instance around the model you plan to run.

Exact EC2 parameters
WHY NOT T2.MICRO OR T3.MICRO

A 1–2 GB RAM free-tier instance will immediately OOM-kill the kernel or container when loading a 7B quantized model alongside PostgreSQL, n8n, FastAPI, and Streamlit.

Next: connecting to the server and installing Docker Engine + log rotation
§ 04 / SERVER SETUP

Install Docker, log rotation & clone repo

Connect via AWS Systems Manager Session Manager and prepare the host before starting containers.

Ubuntu 24.04 commands

In EC2 → Instances → Connect → Session Manager, open a shell and run:

sudo apt-get update
sudo apt-get install -y ca-certificates curl git python3 python3-yaml
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

echo \
  "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu \
  $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

sudo apt-get update
sudo apt-get install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo usermod -aG docker "$USER"

Prevent disk exhaustion with Docker log rotation

sudo tee /etc/docker/daemon.json > /dev/null <<'EOF'
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "20m",
    "max-file": "5"
  }
}
EOF
sudo systemctl restart docker
git clone <YOUR_HYDRAJOB_REPO_URL> ~/HydraJob
cd ~/HydraJob
Next: generating strong secrets and creating your production .env file
§ 05 / SECRETS

Generate credentials & configure .env

Every service reads from a single untracked .env file. Back up N8N_ENCRYPTION_KEY safely.

Environment parameters
Generate random secrets

Run the built-in helper script (it prints fresh keys without committing anything):

cp .env.example .env
python3 supporting_codes/generate_secrets.py
Generate your Caddy Basic Auth password hash

Caddy protects both the Streamlit dashboard and /n8n/ behind Basic Auth in production. Hash your chosen password:

docker run --rm caddy:2-alpine caddy hash-password --plaintext 'YourStrongPasswordHere'

In .env, escape every $ as $$ so Docker Compose does not treat $2a$14... as an env var.

Edit .env with these production values

Next: starting the production stack, pulling the Ollama model, and migrating the database
§ 06 / LAUNCH

Start services, pull Ollama & run migrations

Ollama models are never downloaded automatically on container boot; pull once into the persistent volume.

Startup sequence
# 1. Validate compose config cleanly
python3 supporting_codes/verify_compose.py

# 2. Build and start production stack (postgres, ollama, backend, dashboard, n8n, caddy)
docker compose -f docker-compose.yml -f docker-compose.prod.yml --profile production up -d --build

# 3. Pull your chosen Ollama model into the persistent ollama_data volume
docker compose exec ollama ollama pull qwen2.5:7b-instruct

# 4. Run Alembic database migrations (creates all 13 tables)
docker compose exec backend alembic upgrade head

# 5. Seed the 19 initial companies/sources and 4 search profiles
docker compose exec -e API_BASE_URL=http://127.0.0.1:8000 backend python -c "print('Backend healthy')"
API_BASE_URL="https://hydrajob.yourdomain.com" APP_API_KEY="<YOUR_APP_API_KEY>" \
  python3 supporting_codes/seed_initial_data.py --apply
VERIFY BEFORE MOVING ON

Check https://hydrajob.yourdomain.com/health/ready (should return 200 OK) and confirm docker compose ps shows all 6 containers healthy. Verify ports 5432 and 11434 are NOT reachable from outside the EC2 host.

Next: creating your self-hosted n8n owner account and importing the 4 workflows
§ 07 / N8N SETUP

Create your n8n account & activate workflows

Self-hosted n8n stores your owner account locally in PostgreSQL—no external n8n.cloud account is needed.

Workflow setup
Create the n8n Owner Account

Open https://hydrajob.yourdomain.com/n8n/ (enter your Caddy Basic Auth credentials first). n8n will show its first-run Set up owner account screen. Enter your email, name, and a strong password. Skip any optional telemetry/license prompts.

Create the HydraJob X-API-Key Credential

In n8n, open Credentials → Add Credential → Header Auth:

  • Name: HydraJob X-API-Key
  • Header Name: X-API-Key
  • Header Value: paste your APP_API_KEY from .env
Import all 4 workflows from n8n/workflows/

Use Workflows → Import from File for each of:

  • 01_manual_job_intake.json (Webhook → Ingest → Poll → Evaluate)
  • 02_scheduled_company_scans.json (Every 6h → Scan active sources)
  • 03_search_execution.json (Daily 09:00 IST → Run active searches)
  • 04_retry_and_failure_handling.json (Every 2h → Retry bounded failed sources)
Attach credentials, test, and activate

Open each imported workflow, select HydraJob X-API-Key in every HTTP Request node, click Test workflow once to verify 200/202 responses from http://backend:8000, then toggle the workflow Active.

§ 09 / OPERATIONS

Backups, updates & future Gmail OAuth

Protect PostgreSQL data before upgrades, and only connect Gmail once job discovery and tracking feel solid.

Day-2 operations

Automated PostgreSQL backup cron

mkdir -p ~/HydraJob/backups
# Test manual backup:
docker compose exec -T postgres pg_dump -U hydrajob -d hydrajob | gzip > ~/HydraJob/backups/hydrajob_$(date +%F).sql.gz

Also enable AWS Data Lifecycle Manager daily snapshots for your 80 GB EBS volume.

Zero-drama upgrades

cd ~/HydraJob
git pull
docker compose -f docker-compose.yml -f docker-compose.prod.yml --profile production up -d --build
docker compose exec backend alembic upgrade head

Future Step: Enabling Live Gmail Monitoring (Optional)

The backend already includes the 18-category email classifier, ambiguity-aware application matcher, regression-safe confidence policy (>= 0.90 auto-update, 0.70–0.89 review queue), and 09_Recruitment_Emails.py UI. When you are ready to connect a real inbox:

  • Create a project in Google Cloud Console, enable the Gmail API, and configure an OAuth 2.0 Client using the read-only scope https://www.googleapis.com/auth/gmail.readonly.
  • Create a dedicated Gmail label/filter (e.g., HydraJob-Recruitment) so only job emails are synced.
  • Wire the OAuth token loader into ReadOnlyGmailApiAdapter in backend/app/services/email/gmail_adapter.py and schedule POST /api/v1/emails/sync in n8n.
